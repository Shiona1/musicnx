# Безопасность

Модель: MusicNX — устройство в доверенной LAN, не публичный сервис. Источник —
[SPEC.md](../SPEC.md) §10. **PIN удалён владельцем** (docs/PIN_REMOVAL.md):
мутации в LAN открыты, это принятый residual risk, а не авторизация. Остаются
bind, проверка Host/Origin, `confirm=true` для питания, отсутствие токенов во
frontend, subprocess без shell, redaction логов, path traversal-защита импорта
и шаблона путей. Сервис нельзя выставлять в интернет; усиление доступа —
[ADR-EX-001](EXTERNAL_REVIEW_ACTIONS.md).

## 1. Границы доверия

| Зона | Доверие |
|---|---|
| LAN (дом) | базовое: любые клиенты могут управлять плеером |
| Интернет | **не доверять**, порт не пробрасывать, UPnP не включать |
| Браузер клиента | не доверять: всё валидируется на сервере |
| Яндекс CDN | внешний источник, только HTTPS, ссылки не логировать |

Риск: любой в LAN может управлять плеером/очередью и **всеми мутациями**
(импорт, настройки, downloads, зоны, backup, reboot) — PIN удалён. Это
осознанно принятый residual risk владельцем (docs/PIN_REMOVAL.md), а не
авторизация. Для интернета сервис не предназначен; усиление — ADR-EX-001.

## 2. Host и Origin (anti-DNS-rebinding)

Реализация — middleware в `app/main.py`, проверка WS — в `app/api/websocket.py`.

- `Host` (без порта) допускается, если:
  - входит в `security.allowed_hosts` (default: `localhost`, `127.0.0.1`, `::1`,
    `musicnx.local`; тесты добавляют `testserver`), **или**
  - это IP-адрес из частных диапазонов/loopback (`ipaddress.is_private`,
    `is_loopback`), **или**
  - имя заканчивается на `.local` (mDNS).
- Иначе — `403 host_forbidden`.
- `Origin`, если присутствует: схема `http`/`https`, hostname проходит те же
  правила. Иначе — `403 origin_forbidden`. Для WS — close `1008`.
- CORS не считается авторизацией. `CORSMiddleware` подключается только если
  явно задан `security.allowed_origins`; по умолчанию — нет.
- DNS rebinding дополнительно ломается проверкой Host: атакующий домен
  `evil.example`, резолвящийся в LAN-IP, не пройдёт allowlist.

Ограничение: запросы без `Origin` (curl, старые клиенты) проходят по Host —
это осознанно, иначе ломаются CLI/health-check.

## 3. Модель доступа в LAN (PIN удалён)

**Текущее состояние:** 2026-11-15 владелец удалил PIN (docs/PIN_REMOVAL.md).
**2026-11-16 владелец выбрал вариант A: trusted LAN + принятый риск**
(ADR-EX-001). `require_mutation_access` — no-op; **любой клиент в доверенной LAN**
может импортировать/загружать файлы, менять настройки, запускать
sync/downloads, переключать зоны/Wi-Fi/BT, создавать backup, запускать
maintenance и reboot/shutdown.

Защита, которая остаётся:

- bind на LAN; **не публиковать порт 8080 в интернет**;
- проверка `Host`/`Origin` (anti-DNS-rebinding/CSRF) в `app/main.py` и WS;
- `confirm=true` для reboot/shutdown;
- path traversal guard импорта/upload;
- токены Яндекса только на backend.

Это **принятый residual risk**, а не «полноценная авторизация». Вариант
усиления (admin token/high-risk guard) описан в
[`docs/EXTERNAL_REVIEW_ACTIONS.md`](EXTERNAL_REVIEW_ACTIONS.md) §ADR-EX-001 и
требует решения владельца; до этого не выдавать текущую модель за защищённую.
Legacy-код PIN (`/auth/pin`, `PinStore`) может оставаться в репозитории как
недостижимый, но UI/документация не должны обещать PIN-защиту.

## 4. Токены Яндекса (P3)

- Только backend. Файл токена — вне web root, права `0600`, владелец `musicnx`.
- Refresh делает backend; frontend не видит ни access, ни refresh token.
- Токены не попадают в WS, REST-ответы, логи, сообщения об ошибках.
- `/stream/{track_id}` (P3) сам ходит за подписанным URL на CDN; клиент получает
  только поток байтов MusicNX. Подписанные URL не логируются.
- Logout удаляет файл токена и сбрасывает сессию адаптера.
- При ошибке авторизации — `auth.required` (P3) и понятное сообщение, без
  показа сырых ответов API.

## 5. Секреты и логи

- `logging_setup.py` устанавливает redaction-фильтр: значения ключей
  `token`, `access_token`, `refresh_token`, `authorization`, `password`,
  `secret`, `pin` → `***`. Фильтр применяется к сообщению и аргументам.
- Не логировать query-строки с токенами; аудио-URL с подписью — не логировать.
- `.env`, `config/config.yaml`, `var/` — в `.gitignore`.
- Ошибки наружу — без traceback; полный traceback только в лог.

## 6. Ввод и файлы

- Все SQL-параметры — плейсхолдеры `?`, без конкатенации.
- Пути импорта/загрузок нормализуются и проверяются на выход из корня
  (`resolve().is_relative_to(root)`); шаблон путей вычищает `..` и запрещённые
  символы (реализовано в `app/downloads/paths.py`, тесты P1).
- Никакого shell: только `create_subprocess_exec`/`subprocess.run` со списком
  аргументов. Пользовательские строки не попадают в shell.
- Ограничение размера тела запроса, upload-квоты и общий rate limiting — P0/P1;
  сейчас действует только лимит размера одного upload и path traversal guard.
- JSON-парсинг ограничен pydantic-схемами; неизвестные поля игнорируются.

## 7. WS

- Origin/Host проверяются до `accept`.
- Один клиент не может отправлять серверу ничего, кроме `client.hello`/`ping`;
  неизвестное — `error bad_message`, соединение остаётся.
- Очередь подписчика bounded (drop-oldest), медленный клиент не роняет сервер.
- Состояние в снапшоте не содержит секретов (проверяется тестом, что в снапшоте
  нет ключей `token`, `authorization`).

## 8. Зависимости и обновления

- Версии пинованы (`uv.lock`, `pnpm-lock.yaml`). Обновление — отдельным
  коммитом с прогоном тестов.
- `yandex_music` подключается в P3 и проверяется интроспекцией (AGENTS.md §3).
- Не запускать непроверенные скрипты от имени root; install.sh — идемпотентный,
  проверяет ОС/архитектуру.

## 9. Известные ограничения (честно)

1. **Все мутации открыты в LAN** — любой клиент может импортировать/удалять,
   менять настройки, запускать downloads/sync, переключать зоны и питание.
   Это принятый residual risk (PIN удалён), не «защита». Усиление — ADR-EX-001.
2. **Нет авторизации/сессий** — legacy PIN-код не является действующим
   контролем; UI/документация не должны обещать PIN-защиту.
3. **Нет TLS** — трафик в LAN открыт; для интернета нужен reverse proxy + TLS,
   но это не целевой сценарий v1.
4. **Нет общего rate limiting** — возможен флуд REST/WS и upload из LAN; квоты
   upload — P1, общий rate limit — после решения по security.
5. **Нет CSRF-токенов** — SameSite/Origin-проверка снижают риск, но не заменяют
   авторизацию.
6. **mDNS имя** зависит от avahi и настроек сети; hostname параметризован.

Эти пункты перечислены в PLAN P8; они не маскируются «заглушками».
