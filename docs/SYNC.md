# Синхронизация с Яндекс Музыкой

Требования — [SPEC.md](../SPEC.md) §7.8. **Статус: не реализовано (P6).** Этот
документ фиксирует алгоритм и правила заранее, чтобы P6 не менял модель данных.
До P6 в API нет `/sync/*`, в UI нет Sync Center, фоновых задач нет.

## 1. Режимы

| Режим | Когда |
|---|---|
| `on_startup` | после успешной авторизации и старта backend |
| `hourly` | каждые `sync.interval_s` (по умолчанию 3600 с) |
| `manual` | кнопка/`POST /sync/start` (P6) |
| `smart` | отложено (не делать без команды) |

Расписание живёт в backend; сервер — источник истины, клиенты только отображают
статус. Таймер не запускается, пока не завершена предыдущая синхронизация.

## 2. Один прогон: шаги

```text
1. Проверка сети (NetworkAdapter)      — нет сети → failed(network), локальные данные не трогаем
2. Проверка авторизации                 — нет/истёк токен → failed(auth), refresh; библиотека сохранена
3. Получить список плейлистов           — пагинация, 429 → backoff
4. Для каждого плейлиста:
   a. сравнить revision (если есть)
   b. revision не изменился → skip
   c. revision изменился/нет → fetch полного состава
   d. нормализовать (Track/Artist/Album, mapper)
   e. diff: added / updated / removed
   f. записать в SQLite одной транзакцией на плейлист
5. Обновить счётчики прогона, last_success
6. Отправить WS sync.completed (P6) и обновить UI
7. Записать sync_runs
```

### 2.1 Сравнение ревизий

- Основной путь: `playlists.revision` из API (строка) vs сохранённая.
  Совпала → пропуск без загрузки состава (экономия запросов).
- Fallback: если API не отдаёт ревизию или формат изменился — загрузить состав и
  сравнить множества `(source_id, external_id)` + позиции. Медленнее, но корректно.
- Расхождение схемы адаптера — warning в лог/`sync_runs.error`, не падение.

### 2.2 Diff и идемпотентность

- Ключ трека — `(source_id, external_id)` (для Яндекса `trackId:albumId`).
  Названия не используются как ключ (SPEC §6).
- Added: трека нет в `playlist_tracks` (активном) → вставить в конец позиций.
- Updated: позиция/метаданные изменились → обновить `position`, метаданные трека.
- Removed: трека нет в новом составе → `removed_at = now` (tombstone),
  **локальный файл не удаляется**.
- Повторный прогон на тех же данных не меняет ни одной строки (кроме `synced_at`
  плейлиста) — это критерий приёмки. Счётчики added/updated/removed = 0.
- Позиции после удалений: активные строки сортируются по `position`; новые
  элементы получают `max(position)+1`, чтобы не нарушать `UNIQUE(playlist_id, position)`.
  Периодическая компактификация позиций — отдельной операцией, не обязательна.

### 2.3 Транзакции

- Один плейлист — одна транзакция (атомарность состава).
- Частичный успех: обработанные плейлисты остаются, `sync_runs.status = partial`
  при ошибке на части.
- Метаданные треков/артистов обновляются пакетно (`INSERT … ON CONFLICT`), не
  по одному запросу на трек.

## 3. Правила отказов (SPEC §7.8)

| Ситуация | Поведение |
|---|---|
| Нет сети | Не менять локальные данные; `failed(network)`; следующий запуск по расписанию |
| Ошибка авторизации | Сохранить библиотеку, показать предупреждение, попробовать refresh; `failed(auth)` |
| HTTP 429 | Exponential backoff (2, 5, 15, 30 с; не более 3 повторов), затем failed |
| 5xx/таймаут | Ретрай с backoff, при провале — partial/failed |
| Ошибка одного плейлиста | Продолжить остальные; `partial`; ошибка в `sync_runs.error` |
| Ручной запуск во время идущей | Не создавать вторую задачу; вернуть текущий статус |
| Новый запуск по расписанию при идущем | Пропустить (single-flight), записать причину в лог |
| Отмена (`POST /sync/cancel`) | Отмена между плейлистами; текущая транзакция завершается; `cancelled` |

`last_attempt` и `last_success` **хранятся отдельно** (SPEC §7.8): неудачная
попытка не должна стирать время последнего успеха. Для этого используется
`sync_runs` (max finished_at со status success) + настройки; отдельную колонку
в `playlists` не смешивать с `synced_at` (последний успешный sync плейлиста).

## 4. Статус в API/UI (P6)

`GET /api/v1/sync/status` (P6):

```json
{
  "running": false,
  "last_attempt_at": "2026-11-14T12:00:00.000Z",
  "last_attempt_status": "failed",
  "last_success_at": "2026-11-14T11:00:00.000Z",
  "next_run_at": "2026-11-14T13:00:00.000Z",
  "last_error": {"code": "network", "message": "..."},
  "counts": {"added": 0, "updated": 2, "removed": 1}
}
```

WS-события (P6, зарезервированы SPEC §8): `sync.started`, `sync.progress`,
`sync.completed`, `sync.failed`.

UI Sync Center (P6): последняя/следующая синхронизация, counts, ошибка, кнопка
запуска (disabled при running), история (последние 20 `sync_runs`).

## 5. Не входит в P6

- Загрузка аудиофайлов (это P4, отдельный pipeline).
- «Моя волна» (P3) — ротор-сессии не синхронизируются как плейлисты.
- Двусторонняя синхронизация локальных плейлистов в Яндекс — не делать.
- Smart-режим (адаптивный интервал) — отложен.

## 6. Тесты P6 (план)

- Идемпотентность: два прогона на одних данных → 0 изменений.
- Revision skip: совпавшая ревизия → нет fetch состава.
- Fallback diff без ревизии.
- Удаление из внешнего плейлиста → tombstone, файл на месте.
- 429/backoff/частичный успех/single-flight/отмена.
- Нет сети → данные не изменились.
- `last_attempt` ≠ `last_success` после ошибки.
