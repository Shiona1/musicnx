# ADR — журнал архитектурных решений MusicNX

Формат: контекст → решение → последствия. Записи не удаляются; изменение
решения оформляется новой записью со ссылкой на отменяемую. SPEC.md имеет
приоритет: если ADR противоречит спеке, действует спека, а противоречие
фиксируется здесь.

---

## ADR-001. Принятые решения из SPEC v0.2

**Статус:** принято (базовая линия).
**Контекст:** спецификация утверждена к реализации; стек и ключевые решения
зафиксированы и не пересматриваются.

**Решение:** принимаем целиком §2–§4 SPEC:
Python 3.11+/asyncio/FastAPI, SQLite WAL, mpv как единственный аудиодвижок
(subprocess + JSON IPC, не libmpv), PipeWire + WirePlumber + pipewire-pulse,
BlueZ, Svelte + Vite + TS, REST + WS, systemd user service + linger.
mpv — мастер-клок; браузерная зона играет `/stream` и синхронизируется с
позицией mpv, локальный выход при этом замьючен, но не остановлен.
Позиция в SQLite пишется с debounce, не каждый тик. Токены Яндекса — только
backend. Доступность трека — набор признаков, не один enum. Ссылки на аудио
не хранятся как истина. Без транскодирования; аудиобайты не проходят через Python.

**Последствия:** любые отклонения требуют новой команды и новой ADR. Архитектура
обязана сохранять эти границы в последующих фазах.

## ADR-002. Структура репозитория: backend/ + frontend/ в корне

**Статус:** принято (SPEC §5).
**Решение:** `backend/` — Python-проект с собственным `pyproject.toml` и `uv.lock`;
`frontend/` — Svelte-проект с `package.json` и `pnpm-lock.yaml`. Сборка frontend
идёт в `backend/app/static` (артефакт, не коммитится). Dev-команды — в корневом
`Makefile`.

**Последствия:** на Pi не нужен Node: деплой приносит готовый `static`.
Backend остаётся единственным процессом, отдающим SPA и API.

## ADR-003. Полная схема БД создаётся миграцией 0001 на P0

**Статус:** принято.
**Контекст:** SPEC §6 фиксирует ключевые таблицы, а `docs/DATABASE.md` требует
полную схему уже на P0. Дробить её по фазам — риск миграционного шума и
рассинхронизации документации.

**Решение:** миграция `0001_init.sql` создаёт все таблицы §6 и индексы;
`0002_search.sql` добавляет FTS5-индекс треков. **Поведение** будущих фаз
(импорт, загрузки, синхронизация) при этом не реализуется: таблицы существуют,
но заполняются только тем, что нужно P0/P1 (mock-каталог, очередь, состояние).

**Последствия:** схема стабильна рано; будущие фазы добавляют только колонки/
индексы новыми миграциями. Наличие таблицы не считается реализованной функцией;
в API и UI будущие функции не появляются до своей фазы.

## ADR-004. Восстановление после рестарта — в состоянии `paused`

**Статус:** принято.
**Контекст:** SPEC §7.1 требует восстановления состояния, но не говорит, должен
ли плеер сам заиграть после включения питания.

**Решение:** при старте восстанавливаются очередь, текущий трек и позиция.
Если сохранённый статус `playing`/`buffering`, плеер переходит в `paused` на
сохранённой позиции. Пользователь нажимает Play. Автопродолжение при старте —
не делаем (это не «восстановление», а неожиданный звук в доме).

**Последствия:** acceptance «состояние восстанавливается» выполняется без
неожиданного аудио. Поведение можно изменить настройкой в будущей фазе.

## ADR-005. Mock-режим как первоклассный режим запуска

**Статус:** принято.
**Контекст:** AGENTS.md требует тестов без сети/токена/Pi; P1 требует mock e2e.

**Решение:** `mode: mock | real` в конфиге. В mock:
`MockAudioBackend` (реальное течение времени, seek/pause/eof), mock-адаптеры
Yandex/Router/Bluetooth/Network, сид mock-каталога в БД (источник `mock`).
В real: `MpvAudioBackend`; Яндекс-адаптер и зоны остаются недоступны до P3/P7
и честно репортят `available: false` через system/status.

**Последствия:** один и тот же код Player/Queue/WS работает в обоих режимах;
mock явно виден в API (`mode: "mock"`) и в UI (бейдж «MOCK»).

## ADR-006. mpv IPC: unix socket на Linux, Windows — только mock

**Статус:** принято для P1.
**Контекст:** целевая платформа — Pi (unix socket). Разработка ведётся и на
Windows, где mpv использует named pipes.

**Решение:** реализуется транспорт unix socket (`asyncio.open_unix_connection`)
за интерфейсом `MpvTransport`; логика JSON IPC (кадрирование, корреляция
request_id, observe) тестируется на fake-транспорте. На Windows real-режим с
mpv не поддерживается в P1 и завершается понятной ошибкой конфигурации;
e2e на Windows — mock. Реальная проверка mpv — на Linux/Pi (docs/TESTING.md).

**Последствия:** код IPC полностью реализован и покрыт юнит-тестами без mpv.
Если понадобится Windows named pipe — это отдельная ADR и отдельный транспорт,
без изменения PlayerManager.

## ADR-007. Позиция WS: только видимым клиентам, 2 Гц

**Статус:** принято (SPEC §4.3, §7.10).
**Решение:** сервер шлёт `player.position` не чаще 2 раз/с. Клиент при
подключении и при `visibilitychange` отправляет `client.hello {visible}`;
скрытые вкладки позицию не получают (но получают snapshot/state/track events).
Клиент интерполирует позицию между событиями; дрейф не важен, т.к. аудио в
браузере появится только в P3.

**Последствия:** экономия трафика и CPU на слабом сервере; в UI позиция
обновляется плавно локальным тикером.

## ADR-008. Формат ошибок REST и WS-конверта

**Статус:** принято.
**Решение:** REST-ошибки: `{"error": {"code": "not_found", "message": "...",
"details": {}}}` с HTTP 400/404/409/422/500. WS-конверт: `{type, ts, payload}`,
`ts` — RFC3339 UTC с миллисекундами. REST-успехи возвращают ресурс целиком
(например, состояние плеера или очередь), без обёртки `data`.

**Последствия:** единый разбор ошибок и событий на клиенте; коды — стабильные
строки, тексты можно менять.

## ADR-009. Авторизация UI: мини-PIN в P1.2, полный polish в P8

**Статус:** обновлено 2026-11-14 (ранее: отложено до P8); mini-PIN реализован
в P1.2/P2.
**Контекст:** SPEC §10 требует PIN/сессию для импорта и изменения настроек.
P2 вводит импорт, поэтому защита нужна раньше, чем полный P8-полишинг
(сессии в БД, rate limit, CSRF-токены, смена PIN из UI).

**Решение (P1.2/P2):**
- `security.pin` в config/env. Если PIN задан — изменяющие запросы требуют
  подписанную сессионную cookie (`HttpOnly`, `SameSite=Strict`, `Path=/`,
  `Secure` при HTTPS) после `POST /api/v1/auth/pin`.
- Если PIN **не** задан — изменяющие эндпоинты принимаются только с loopback
  (`127.0.0.1`/`::1`). Удалённый запрос получает `403 pin_required`.
- Host/Origin allowlist действует на все запросы (anti-DNS-rebinding);
  несовпадение Origin → `403 origin_forbidden`.
- Read-only эндпоинты (`player`, `queue`, `library` GET, будущий `stream`)
  остаются открытыми в LAN-модели MVP — ADR-021.
- PIN и session secret не пишутся в логи/ответы; PIN никогда не отдаётся API.

**Последствия:** импорт защищён до появления UI логина; P8 добавляет полный
полишинг (хранение хэша PIN, смену PIN, истечение сессий в БД, rate limiting,
TLS-рекомендации). До P8 сервис не публиковать в интернет.

## ADR-010. Громкость — целое 0..100

**Статус:** принято.
**Контекст:** mpv принимает 0..100, БД `audio_zones.volume` — число.

**Решение:** API и состояние используют целое 0..100. Значения вне диапазона
отклоняются 422. Последняя громкость хранится в `settings` (`player.volume`).

**Последствия:** никаких дробных процентов и преобразований единиц в P1.

## ADR-011. `previous`: перемотка в начало, если прошло > 3 с

**Статус:** принято.
**Решение:** при позиции > 3000 мс `previous` перематывает текущий трек в 0;
иначе переключает на предыдущий элемент очереди. Поведение как у обычных
плееров, предсказуемо для пользователя.

**Последствия:** уточняется тестами state machine; при желании меняется настройкой.

## ADR-012. Очередь уникальна по позиции, трек может повторяться

**Статус:** принято (SPEC §6).
**Решение:** `queue_items.position` уникален; при вставке/удалении/перестановке
позиции перенумеровываются в одной транзакции. Один и тот же `track_id` может
встречаться в очереди несколько раз (разные `queue_items.id`). Восстановление
идёт по `queue_items.id`, а не по треку.

**Последствия:** reorder принимает полный список `item_ids` (перестановку),
иначе 409; удаление текущего элемента останавливает воспроизведение и выбирает
следующий по позиции (или `stopped`, если очередь пуста).

## ADR-013. Event bus: bounded-очереди, позиции вытесняются первыми

**Статус:** принято (обновлено 2026-11-14 после P1.2).
**Решение:** у каждого WS-клиента asyncio.Queue(maxsize=256). При переполнении
удаляется старейшая **позиция**, а не произвольное событие; если позиций в
очереди нет, входящая позиция отбрасывается. Критичные события
(`player.track_changed`, `queue.updated`, `library.*`, `player.state_changed`)
не вытесняются позиционным потоком. Состояние всегда восстанавливается
снапшотом.

**Последствия:** backpressure не роняет сервер и не теряет смену трека/очереди;
позиция может потеряться — это допустимо (UI интерполирует и получает снапшот).
Тест: `test_event_bus.py::test_critical_track_event_survives_position_overflow`.

## ADR-014. Сборка frontend не коммитится; проверка статики — на релизе

**Статус:** принято.
**Решение:** `backend/app/static` в `.gitignore` (кроме `.gitkeep`). CI/деплой
собирает `make build`. Backend, не найдя `index.html`, отдаёт JSON-подсказку
на `/`, а не падает.

**Последствия:** репозиторий чистый; для ручной проверки UI нужен `make build`
или Vite dev server.

## ADR-015. E2E на P1 — через mock backend и два WS-клиента

**Статус:** принято.
**Контекст:** P1 требует «mock e2e без токена и без Pi» и синхронизацию двух вкладок.

**Решение:** e2e-тесты поднимают приложение с `mode=mock`, временной БД и
`MockAudioBackend`; проверяют play/pause/seek/next, восстановление после
перезапуска и одинаковые снапшоты двух WS-клиентов. Браузерная проверка —
Playwright вручную/в CI на dev-машине.

**Последствия:** тесты детерминированы (реальные короткие sleep только для
тикера позиции), не требуют mpv и сети.

## ADR-016. `index.html` не кэшируется, хэшированные ассеты — можно

**Статус:** принято (по итогам проверки на Pi 14.11.2026).
**Контекст:** после деплоя новой сборки браузер показал старый UI: `index.html`
отдавался с `ETag`/`Last-Modified`, а имя JS-ассета изменилось. Пользователь
видит «MOCK»/старые данные, хотя сервер уже обновлён.

**Решение:** FastAPI отдаёт `index.html` (и SPA-fallback) с
`Cache-Control: no-cache, must-revalidate`. Файлы `/assets/*` содержат хэш в
имени и могут кэшироваться браузером надолго.

**Последствия:** обновление UI доезжает до клиента без ручного hard-reload;
лишних запросов к API это не добавляет. Если понадобится offline-PWA, политика
пересматривается вместе с service worker (P8).

## ADR-017. mpv: ждать `file-loaded`, EOF только по `reason=eof`

**Статус:** принято (по итогам проверки на Pi 14.11.2026).
**Контекст:** `loadfile` отвечает раньше, чем файл готов к seek. Немедленный
`seek` (resume с позиции, seek после play) падал с `error running command`.
Кроме того, `end-file` приходит и при замене файла (`reason: "stop"`); если
считать его EOF, resume останавливал трек сразу после загрузки.

**Решение:** после `loadfile` ждать событие `file-loaded` (с таймаутом), затем
ставить pause и выполнять seek. `end-file` считается EOF только при
`reason == "eof"`; `eof-reached` остаётся дополнительным сигналом. Ошибка seek
превращается в `503 unavailable`, а не `500`.

**Последствия:** resume/seek/переключение трека работают на реальном mpv;
тесты IPC покрывают оба случая (`test_mpv_ipc.py`). Задержка загрузки теперь
явная (до `audio.start_timeout_s`), а не гонка.

## ADR-018. Тест на 32-bit Pi не меняет целевой baseline

**Статус:** заменено ADR-019 (2026-11-14): 32-bit `armv7l` теперь **допускается**
на Pi 3; 64-bit остаётся рекомендацией. Запись сохранена как история решения.
**Контекст:** доступное устройство — Raspberry Pi 3 B с 32-bit Raspberry Pi OS 13
(`armv7l`), тогда как SPEC §2 фиксирует 64-bit Lite. P1 проверен на 32-bit.

**Решение:** целевой платформой остаётся Raspberry Pi OS Lite 64-bit. 32-bit
считается тестовой средой; код и зависимости от архитектуры не зависят
(pydantic-core/uvloop/websockets ставятся из piwheels). Отклонение и результаты
зафиксированы в docs/HARDWARE.md §9; отдельного кода/обходов не добавляем.

**Последствия:** перед приёмкой v1 рекомендуется перепрошить 64-bit и повторить
hardware-чеклист. Если 64-bit окажется недоступен, это отдельное решение
владельца, а не тихое изменение spec.

## ADR-019. 32-bit `armv7l` допускается на Pi 3

**Статус:** принято 2026-11-14 (санкционированная поправка SPEC §2).
**Контекст:** целевая ОС в SPEC — Raspberry Pi OS Lite 64-bit. Фактическое
устройство работает на 32-bit Trixie (`armv7l`), P1 real-прогон успешен.
Перепрошивка сейчас не санкционирована владельцем.

**Решение:** целевой рекомендацией остаётся 64-bit; 32-bit `armv7l` на Pi 3
(1 ГБ) **допускается**, если нативные зависимости ставятся и проверены на
устройстве (piwheels/wheels). Это фиксируется в SPEC §2 и docs/HARDWARE.md.

**Последствия:** установка на 32-bit не считается ошибкой. Перед P4 — отдельный
gate: проверить установку `yandex-music[async,crypto]` на `armv7l`; результат
записать в HARDWARE. Если пакет не ставится — поднять флаг и обсудить с
владельцем; автоматически не перепрошивать.
**Результат gate (2026-11-14):** `yandex-music 3.2.2` + aiohttp/cryptography
armv7l ставятся через piwheels (docs/HARDWARE.md §9). P4 разблокирован по
зависимостям; сама P4 не начата.

## ADR-020. Пользователь и hostname параметризованы

**Статус:** принято 2026-11-14 (санкционированная поправка SPEC §12).
**Контекст:** прежние тексты хардкодили `musicnx.local` и пользователя
`musicnx`; фактическая установка может использовать другие имена.

**Решение:** установка и документация используют параметры
`<hostname>`/`<user>` с дефолтами `musicnx`/`musicnx`. Существующая установка
под другим именем допустима и не переименовывается. В коде/скриптах нет обязательного
`musicnx.local`; allowlist mDNS принимает `*.local`, а конфиг задаёт реальные
имена. `install.sh` (P8) выводит адрес `http://<hostname>.local:8080`.

**Последствия:** деплой переносим между устройствами; документация не ломается
на существующем hostname. Тесты используют `testserver`/`*.local`, а не
конкретный `musicnx.local`.

## ADR-021. Read-only API открыт в LAN MVP, mutations защищены

**Статус:** принято 2026-11-14.
**Контекст:** мини-PIN (ADR-009) защищает импорт (настройки — P8), но UI должен
работать без логина для просмотра и управления плеером.

**Решение:** открыты без PIN: `GET /player/*`, player-команды? **Нет** —
`POST /player/*` и `POST/DELETE /queue/*` тоже считаются интерактивным
управлением, но не импортом/настройками. В LAN MVP они остаются открытыми,
как и в P1. Защищены: `POST /library/import` (реализован в P2 и защищён
mini-PIN/localhost) и будущие `PUT /settings`, `POST /sync/*`,
`POST /downloads*`, `POST /zones/*`, `POST /bluetooth/*`.
Read-only library/artwork/stream также открыты.
**Граница:** любой, кто в LAN, может управлять плеером и очередью; менять
библиотеку/настройки — только с PIN (или localhost без PIN).

**Последствия:** UI не требует логина для основного сценария; импорт защищён.
P8 может расширить защиту настройками, но не должен ломать LAN-MVP без команды.

## ADR-022. Идентичность и дедупликация локальных файлов

**Статус:** принято 2026-11-14.
**Контекст:** локальные файлы не имеют внешнего ID; один трек может быть в
MP3/FLAC/AAC с разной длительностью из-за padding контейнера.
**Решение:** источник `local`, `external_id = local:<relative_path>` внутри
корня импорта. Дедупликация: сначала `(source_id, external_id)`, затем
title+artists+album+duration с допуском **1500 мс**. Только по названию не
склеиваем; разные album/artist/длительность дают отдельный трек. Несколько
файлов одного трека — несколько `media_files`, путь уникален.
**Последствия:** повторный импорт идемпотентен; перекодированный файл в другой
формат остаётся одним треком, а ремикс с другим альбомом — разным.

## ADR-023. FTS5 как обычная таблица + rebuild при старте

**Статус:** принято 2026-11-14.
**Контекст:** contentless FTS5 (миграция 0002) не позволял удалять/обновлять
строки; при импорте и изменении тегов индекс нужно поддерживать.
**Решение:** миграция 0003 пересоздаёт `tracks_fts` как обычную FTS5-таблицу;
импорт делает delete+insert по `rowid`; при старте, если
`COUNT(tracks) != COUNT(tracks_fts)`, индекс перестраивается. Поисковый запрос
очищается до букв/цифр и использует prefix-токены.
**Последствия:** старые БД автоматически чинятся при старте; удаление
заброшенных строк больше не мусорит; перестройка на большой библиотеке — P8
(сейчас P2 объёмы).

## ADR-024. Offline только после checksum; обложки в LRU-кэше

**Статус:** принято 2026-11-14.
**Контекст:** SPEC требует честный offline и не хранить временные файлы; Pi 3
слабый, тяжёлые операции нельзя делать в event loop.
**Решение:** импорт регистрирует `media_files` без `verified_at`;
`tracks.has_local_file` становится 1 только после SHA-256 проверки (в worker
thread). Обложки извлекаются embedded art, режутся в 300/1000/64 (64 pre-blur),
пишутся атомарно в `paths.cache/covers`, лимит `library.cover_cache_mb` с
удалением самых старых. Temp-файлы старше часа чистятся.
**Последствия:** до проверки трек не выглядит offline; пропавший файл помечает
`file_missing`; кэш не растёт бесконтрольно. P4 может переиспользовать кэш.

## ADR-025. Yandex API: версия 3.2.2 и замороженный список методов

**Статус:** принято 2026-11-14.
**Контекст:** библиотека `yandex_music` быстро меняет сигнатуры; выдуманный
метод ломает P3 и вводит в заблуждение.
**Решение:** пин `yandex-music==3.2.2`; перед P3 выполнена интроспекция
`ClientAsync` и сверка с ym.marshal.dev. Все используемые методы и сигнатуры
записаны в `docs/YANDEX_API.md`; вызов метода вне документа запрещён.
**Последствия:** обновление библиотеки требует повторного gate и правки
документа; mock и real используют один `YandexAdapter`.

## ADR-026. Токены: файл 0600, proactive refresh, никаких токенов наружу

**Статус:** принято 2026-11-14.
**Решение:** `TokenStore` пишет `access_token/refresh_token/expires_in/
obtained_at/login/source` атомарно в файл 0600 вне web root. Refresh —
OAuth `grant_type=refresh_token` (в 3.2.2 метода refresh нет), проактивно за
`refresh_before_s` и один retry на 401; failure → WS `auth.required`. API/WS
отдают только `{authenticated, login, expires_at, source}`. PIN/токены не
логируются.
**Последствия:** Device Flow можно возобновить после рестарта; файл надо
бэкапить отдельно; смена/отзыв токена — P8.

## ADR-027. Yandex-каталог нормализуется в общие tracks (не отдельная таблица)

**Статус:** принято 2026-11-14.
**Решение:** Yandex-треки/альбомы/артисты upsert-ятся в общие `tracks`/
`albums`/`artists` + `track_sources(source='yandex', external_id='<track>:<album>')`;
очередь/плеер/поиск работают с внутренними track_id. Плейлисты — отдельная
кэш-таблица. `/stream/{track_id}` сначала ищет локальный файл, иначе direct
link Yandex. Ссылки временные, получаются перед каждым использованием.
**Последствия:** единая библиотека и будущий P6 sync; дубликаты local/yandex
пока не сливаются по метаданным (P6).

## ADR-028. Волна: rotor station + аккаунт-лайки для like/dislike

**Статус:** принято 2026-11-14.
**Контекст:** документированные типы `rotor_station_feedback` — только
`radioStarted`, `trackStarted`, `trackFinished`, `skip`; like/dislike там не
подтверждены.
**Решение:** треки — `rotor_station_tracks('user:onyourwave', queue=last_id)`;
skip — `rotor_station_feedback(..., 'skip', track_id, total_played_seconds)`;
like/dislike — `users_likes_tracks_add/remove` и
`users_dislikes_tracks_add/remove`. Refill при <3 треках. Сессия волны
in-memory (рестарт = новая волна).
**Последствия:** никаких неподтверждённых rotor-типов; like влияет на аккаунт,
а не на конкретную станцию; генеративные станции — позже.

## ADR-029. Browser zone: mpv — мастер-клок, локальный вывод muted

**Статус:** принято 2026-11-14.
**Решение:** `audio.browser_zone=true` → после загрузки трека backend вызывает
`AudioBackend.set_muted(True)`; клиент играет `/stream/{track_id}` в `<audio>`,
синхронизируется по `player.position` (дрейф >0.5 с → seek). `/system/status`
отдаёт `audio.browser_zone`. По умолчанию false (обычный локальный выход).
**Последствия:** один трек не звучит дважды; браузерный клиент должен уметь
autoplay (иначе кнопка «Включить звук»); P7 заменит флаг реальными зонами.

## ADR-030. Power risk принят владельцем: real operations разрешены

**Статус:** принято 2026-11-14 по решению владельца.
**Контекст:** Pi 3 под нагрузкой даёт under-voltage (`0x50005`), замена БП не
устранила; gate блокировал real-import/download/soak.
**Решение:** владелец принял риск. Real-import/download/soak разрешены; при
странных сбоях/повреждениях логировать `vcgencmd get_throttled`, но не
блокировать. Перед первой real-записью — backup SQLite через Backup API.
**Последствия:** возможны заикания/повреждения при нестабильном питании; это
осознанный риск, не баг MusicNX. `get_throttled` остаётся диагностикой.

## ADR-031. P4 download task: одна строка на трек; качество не хранится

**Статус:** принято 2026-11-14.
**Контекст:** таблица `download_tasks` из P0 имеет `UNIQUE(track_id)` и не
содержит `quality/format`; менять схему ради P4 MVP не стали.
**Решение:** один task на трек; фактический формат выводится из расширения
`target_path` и отдаётся в `DownloadTask.format`; `quality` может быть null.
Повторный POST для verified/completed не создаёт дубль. `media_files` готов к
нескольким качествам, но UI/очередь P4 — одно.
**Последствия:** несколько качеств одного трека как отдельные задачи — P6/P4.1;
миграция quality/format — при необходимости. Offline/format badge честные.

## ADR-032. Lyrics: свой LRC parser, кэш, offset per track

**Статус:** принято 2026-11-14.
**Решение:** LRC парсится своим parser (без внешней зависимости):
`[mm:ss.xx]`, несколько меток, `[offset:]`, plain fallback. Источник:
local `.lrc` рядом с media → Yandex `tracks_lyrics` LRC/TEXT → SQLite cache.
`offset_ms` хранится в `lyrics` per track и применяется UI к подсветке/seek;
per-zone offset — P7. Клик по строке → seek; `lyrics.updated` обновляет
открытые вкладки. Mock даёт детерминированные 3 строки.
**Последствия:** текст не логируется; Yandex недоступен → available=false,
не 500; negative cache/single-flight — P6/P8.

## ADR-033. Sync: composition diff, single-flight, no destructive playlist removal

**Статус:** принято 2026-11-14.
**Контекст:** `YandexPlaylist` DTO не содержит `revision`; удаление плейлистов
из Яндекса не должно удалять локальные данные/очередь.
**Решение:** сравнивать composition (`playlist_tracks`) до/после; `replace`
только при изменении; один прогон (409), ошибка плейлиста → partial; backoff
2 s/8 s, 3 попытки для retryable; `playlists_removed=0`. Revision fast-path —
когда DTO расширят. `sync_runs` хранит counts/error; hourly только при
`sync.enabled`; manual всегда.
**Последствия:** идемпотентно; удалённые из Яндекса плейлисты не стираются
локально (P8 может добавить tombstone); real manual sync 668 треков проверен.

## ADR-034. Zones: mock-first PipeWire/BT with real pactl/bluetoothctl fallback

**Статус:** принято 2026-11-14.
**Решение:** `ZoneManager` + `ZoneRouter`; mock без железа, real PipeWire через
`pactl` (list/default/move sink-input/volume) без shell; BT через `bluetoothctl`
или mock, если утилиты нет. Переключение зоны не останавливает player; volume/
offset хранятся в `audio_zones`; WS `zones.updated`/`bt.device_*`.
**Последствия:** реальное железо (USB-DAC/BT) не проверено; fallback не
притворяется A2DP; PIN на mutations.

## ADR-035. PIN rotation: scrypt in var/secrets; TLS optional for LAN

**Статус:** принято 2026-11-15 по решению владельца.
**Решение:** `POST /auth/pin/change` проверяет текущий PIN, пишет scrypt-хэш в
`var/secrets/pin.json` (0600) и выдаёт новую cookie; config.yaml остаётся
bootstrap/fallback. Rate-limit неудач персистентный (`pin_attempts.json`, хэш
IP). TLS для v1 не требуется: сервис LAN-only на 8080; reverse proxy/Caddy —
опционально, вне acceptance.
**Последствия:** смена PIN доступна из Settings; старые сессии живут до TTL,
новая cookie выдаётся сразу; plaintext PIN не хранится/не логируется.

## Возражения и расхождения с SPEC (на момент P1)

1. **SPEC §13 P1 требует тест «шаблон путей», хотя загрузки — P4.** Реализован
   чистый модуль шаблона путей (`downloads/paths.py`) и его тесты без пайплайна
   загрузок. Это не реализация P4.
2. **SPEC §10 требует PIN; фазы содержали его только в P8.** Мини-PIN сделан
   раньше — в P1.2 (ADR-009): `security.pin`, подписанная сессия и
   `require_mutation_access`. Полный P8-полишинг (хэш PIN, смена из UI,
   rate limit, CSRF, TLS-рекомендации) остаётся; это ограниченная реализация,
   а не имитация.
3. **SPEC §7.10 говорит «только активным клиентам» без определения «активного».**
   Определили как «видимая вкладка» (ADR-007).
4. **SPEC §13 P1 упоминает LRC parser как возможный к переносу на P5.** Перенесён:
   в P1 его нет, тесты P5.
